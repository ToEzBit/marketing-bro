# 0006 — Browser: เข้าคิวรอแทนการปฏิเสธ

Status: accepted (2026-08-03)

## Context

ADR 0003 ให้ Task ที่ขอ Browser ระหว่างที่ Task อื่นถืออยู่ "ถูกปฏิเสธ ไม่เข้าคิว" โดยเดิมพันว่าทีมเล็ก โอกาสชนต่ำ ใช้งานจริงแพ้เดิมพันสองชั้น:

1. lock เคยรั่ว (ค้างจน session ตาย ~30 นาที ทั้งที่หน้าต่างปิดแล้ว — แก้แล้ว: ปล่อยตอนจบเทิร์น) ทำให้การปฏิเสธเกิดถี่กว่าการชนจริงมาก
2. ที่สำคัญกว่า: Agent ที่โดนปฏิเสธไม่ยอมแพ้ — มันใช้ `ScheduleWakeup` (tool ฝั่ง harness ของ Claude Code CLI ที่**ไม่ผ่าน** `canUseTool`/Approval) ตั้งปลุกตัวเองแบบ backoff ทุก 2–15 นาที **สร้างคิวเถื่อนของตัวเอง**: เผา 7 เทิร์นใน 20 นาทีโดยไม่ได้อะไรกลับมา ไม่มีลำดับยุติธรรม (ใคร poll ตอน lock หลุดพอดีคือได้) และบอทมองไม่เห็นลูปนี้เลย

ความต้องการเข้าคิวจึงมีจริงถึงขั้นโมเดลประดิษฐ์เอง — เวอร์ชันที่ระบบควบคุมย่อมดีกว่าเวอร์ชันด้นสดทุกมิติ

## Decision

- การชน Browser ไม่จบด้วย deny อีกต่อไป: browser tool call ที่ policy อนุญาตแล้ว **ค้างรอใน `BrowserQueue` (FIFO)** ผ่านกลไก `canUseTool` — วิธีเดียวกับที่ Approval ค้างรอปุ่มมนุษย์อยู่แล้ว ระหว่างรอโมเดลไม่ inference ไม่เผาโทเคน และเมื่อคนถือปล่อย (จบเทิร์น) หัวคิวไปต่อทันที
- **Task ปกติรอไม่จำกัดเวลา** — เธรดเห็นสถานะว่ารอใครอยู่ คิวที่เท่าไร และมนุษย์คือ timeout ที่ฉลาดที่สุด (`/stop` ได้ทั้งฝั่งคนรอและคนถือ)
- **Run ของ Schedule รอได้อย่างมากถึงเวลารอบถัดไปของตัวเอง** (เส้นตายธรรมชาติ ไม่ใช่เลขคงที่) — ครบเส้นตายแล้วยังไม่ถึงคิว: รอบนั้นจบเป็น failure (นับเข้า auto-pause 3 ครั้งตาม ADR 0004) และรอบใหม่เข้าคิวแทนจากท้ายแถว → schedule หนึ่งมีงานรอในคิวได้ทีละหนึ่งเสมอ ในทางปฏิบัติเส้นตายถอยมาก่อนเวลารอบถัดไปเล็กน้อย (90 วินาที) เพื่อให้รอบที่แพ้ปิดเทิร์นทันก่อนรอบใหม่ยิง — ไม่งั้นรอบใหม่จะโดนข้ามฐาน "รอบก่อนยังทำไม่เสร็จ" เสียทั้งรอบ
- **ไม่มี auto-retry แบบหน่วงเวลา** — event-driven ตลอดหน้าต่างระหว่างรอบคือ retry ที่ดีที่สุดแล้ว
- pre-flight gate ของ scheduler ("ข้ามรอบเพราะ Browser ถูกใช้อยู่") ถูกตัดออก — หมดหน้าที่
- การอนุมัติต่อ Task (ครั้งแรกถาม, ที่เหลือผ่าน, upload/run_code ถามทุกครั้ง — ADR 0002/0003) **คงเดิมทุกประการ** และแยกขาดจากการถือ/การรอคิว
- system prompt บอก Agent ตรง ๆ ว่า browser call ที่ช้าคือการรอคิว ห้ามตั้ง retry/wakeup เอง — และเมื่อไม่มีคำ deny ให้เห็น ลูป ScheduleWakeup ก็ไม่มีเหตุให้เกิดตั้งแต่ต้น

## Considered Options

- **Fixed-delay retry** (ล้มแล้วนัดลองใหม่ในอีก N นาที) — ปัดตก: เดาเวลา มีโอกาสตื่นมาชนช่วงไม่ว่างซ้ำแล้วล้มอีก และต้องสร้างกลไกแยกชนิดความล้มเหลว + กันนัดชนรอบถัดไป
- **Timeout สั้น (10 นาที) + ระบบ retry** — ปัดตก: สองกลไกซ้อนกันเพื่อเลียนแบบสิ่งที่คิว event-driven ให้ฟรี ๆ
- **Isolated browser / หลาย profile** สำหรับงานที่ไม่ใช้ login — เก็บไว้เป็นทางอัพเกรดเมื่องาน scraping มาจริง ไม่จ่ายต้นทุนวันนี้
- **แบน `ScheduleWakeup` ผ่าน disallowedTools** — ไม่ทำ: เมื่อคิวลบคำ deny ออกจากสมการ ลูปตายเองโดยธรรมชาติ และ tool นี้อาจมีประโยชน์ชอบธรรมในงานอื่น

## Consequences

- ✅ ไม่มีเทิร์น/โทเคนสูญเปล่ากับการ poll, ลำดับยุติธรรมมาก่อนได้ก่อน, schedule ไม่พลาดทั้งรอบเพราะการชนสั้น ๆ หลักวินาที
- ⚠️ tool call ของผู้รอค้างเปิดได้นาน (Task: ไม่จำกัด) — ยอมรับโดยให้มนุษย์เป็นคนปิดผ่าน `/stop` และ abort signal ของ tool call พาผู้รอออกจากคิวเสมอเมื่อ session จบ/ถูกยกเลิก
- ⚠️ ถ้า Agent ผู้ถือฝ่าฝืนคำสั่งแล้วไม่ปิดหน้าต่างก่อนจบเทิร์น ผู้รอที่ได้คิวถัดไปจะเจอ ProcessSingleton ตอน launch — system prompt มีทางรายงานให้ผู้ใช้อยู่แล้ว
- Supersede: ข้อ "ปฏิเสธ ไม่เข้าคิว" ของ ADR 0003 และการข้ามรอบเพราะ browser ไม่ว่างของ ADR 0004
