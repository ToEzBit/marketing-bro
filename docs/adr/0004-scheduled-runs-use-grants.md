# 0004 — Scheduled Run ใช้ Grant ตอนสร้างแทน Approval ตอนรัน

Status: accepted (2026-07-31)

> ⚠️ ข้อ "Browser ต้องเลือกมอบเพิ่มตอนสร้าง" ถูกยกเลิกแล้วโดย
> [ADR 0012](./0012-scheduled-runs-always-have-browser.md) (2026-08-19) — ทุก Run ใช้ browser ได้เสมอ
> ส่วนที่เหลือของ ADR นี้ยังใช้อยู่ทั้งหมด รวมถึงเพดานที่ปฏิเสธเสมอ (เขียนนอก Workspace, รันโค้ดระดับ Host)

## Context

Schedule คืองานที่บอทยิงซ้ำเองตามรอบเวลา (เช่น โพสต์คอนเทนต์ทุกเช้า) โดยไม่มีคนเฝ้า
โมเดล Approval ของ ADR 0002 พึ่งมนุษย์กดปุ่มตอนรัน — ใช้กับ Scheduled Run ไม่ได้
เพราะปุ่มจะค้างจน timeout แล้วงานพังทุกรอบ use case หลักคืองานคุม Browser
(โพสต์อัตโนมัติ) จึงจำกัดให้เหลือแค่ read-only ก็ไม่ได้เช่นกัน

## Decision

ย้ายจุดอนุมัติจาก "ตอนรัน" ไป "ตอนสร้าง Schedule" — ตอนสร้างมีมนุษย์อยู่เต็มตัว
ให้จุดนั้นเป็นจุดตัดสินใจแทน เรียกว่า **Grant**:

- **พื้นฐานทุก Schedule:** อ่าน/เขียนไฟล์ใน Workspace + Bash ทุกคำสั่ง ผ่านอัตโนมัติ
- **Browser ต้องเลือกมอบเพิ่มตอนสร้าง** (`browser` grant) — ครอบคลุมการคุมเว็บเต็มรูปแบบ
  รวม `browser_file_upload` (จำเป็นสำหรับงานโพสต์) Schedule ที่ไม่ได้มอบ แตะ browser ไม่ได้เลย
  (`/schedule edit browser:` ให้หรือถอน grant นี้ทีหลังได้ — จุดตัดสินใจยังเป็น "ตอนที่มีคนอยู่"
  เหมือนเดิม ไม่ใช่ตอนรัน และไม่ขยายอำนาจใคร: คนที่แก้ได้คือเจ้าของกับ Operator ซึ่งแคบกว่า
  ตอนสร้างที่ Member ทุกคนมอบ grant ได้อยู่แล้ว และเดิมก็ทำได้ด้วยการ delete แล้ว create ใหม่
  ทุกครั้งที่แก้ บอทโพสต์สรุปสิ่งที่เปลี่ยนลง thread ของ Schedule ให้ audit เห็น)
- **ปฏิเสธเสมอไม่ว่ามอบอะไรไว้:** เขียนไฟล์นอก Workspace และ `browser_run_code_unsafe`
  (รันโค้ดระดับ host — เปิดไว้เท่ากับยกเลิกทุกขอบเขตข้างบน)
- Scheduled Run **ไม่มีทางถามมนุษย์** — ทุก decision จบที่ allow หรือ deny ทันที
  agent ที่โดน deny ต้องปรับวิธีหรือรายงาน ไม่มีอะไรค้างรอ
- Member ทุกคนสร้าง Schedule และมอบ browser grant ได้ — หลักคือ "ย้ายจุดอนุมัติ
  ไม่ใช่ขยายอำนาจ": Member อนุมัติ browser ให้งานตัวเองได้อยู่แล้วตาม ADR 0003

กลไกความปลอดภัยที่เหลือเมื่อไม่มีคนเฝ้าตอนรัน:

- ทุก Run เขียน activity log ลง thread ถาวรของ Schedule — audit ย้อนหลังได้เสมอ
- `pause` กดได้โดย Member ทุกคน (เบรกฉุกเฉินต้องง่ายกว่าคันเร่ง)
- ล้มเหลว 3 รอบติด → auto-pause + แจ้งเจ้าของ (การข้ามรอบไม่นับเป็นล้มเหลว)
- Engine ไม่ยิงชดเชยรอบที่พลาดเอง (บอท offline / รอบก่อนไม่เสร็จ → ข้าม + จดเหตุผล)
  — มนุษย์สั่งรันซ้ำเองผ่านปุ่ม/`/schedule run`
  (เดิมเคสนี้รวม "browser ไม่ว่าง" ด้วย — ตั้งแต่ ADR 0006 รอบไม่ถูกข้ามเพราะ browser
  ไม่ว่างอีกแล้ว มันเข้าคิวรอแทน โดยรอได้อย่างมากถึงเวลารอบถัดไปของตัวเอง)

## Considered Options

- **จำกัด Scheduled Run เป็น read-only** — ปลอดภัยสุด ไม่แตะ ADR 0002 แต่ตัด use case
  หลัก (โพสต์ผ่าน browser) ทิ้งทั้งหมด
- **Auto-approve ทุกอย่างไม่มีเพดาน** — เรียบง่ายกว่า แต่ schedule สายรายงานที่ไม่ใช้
  browser จะถือสิทธิ์บัญชีที่ล็อกอินไว้ฟรี ๆ และการเขียนนอก Workspace/รันโค้ดระดับ host
  ไม่มี use case ที่ชอบธรรมใน scheduled งานเลย — เปิดไว้มีแต่ downside
- **Approval เด้งตามปกติแล้วปล่อย timeout** — งานพังเงียบ ๆ ทุกรอบ ไม่ตอบโจทย์

## Consequences

- ⚠️ **ความเสี่ยงที่รับไว้โดยรู้ตัว:** Schedule ที่มี browser grant และไปอ่านเนื้อหาเว็บ
  ภายนอก อาจโดน prompt injection ให้ใช้บัญชีที่ล็อกอินค้างทำสิ่งที่ไม่ได้ตั้งใจ ตอนที่
  ไม่มีใครดู — ด่านมนุษย์ของ ADR 0002/0003 ไม่มีอยู่ใน Scheduled Run โดยออกแบบ
  ตัวลดความเสี่ยงคือ audit log + emergency pause + auto-pause เท่านั้น
- Bash ใน Scheduled Run ผ่านหมดทุกคำสั่ง — ขอบเขต "ห้ามเขียนนอก Workspace" บังคับได้จริง
  เฉพาะ tool แก้ไฟล์ (Write/Edit) ที่บอทเห็นพาธ ไม่ครอบคลุมสิ่งที่ Bash ทำเองได้
- Run แต่ละรอบเป็น Agent Session ใหม่เสมอ ไม่สืบความจำ — ความจำข้ามรอบเป็นหน้าที่ของ
  prompt + ไฟล์ใน Workspace (เช่น CLAUDE.md ของ workspace, ไฟล์ posted.md)
