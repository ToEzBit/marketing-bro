# 0011 — Content Calendar: ขั้นสุดท้ายของ pipeline อิงเวลาที่คนวางไว้

Status: accepted (2026-08-19)

แก้ไข ADR 0007 บางส่วน (ดูหัวข้อ "สิ่งที่กลับด้านจาก ADR 0007")

## Context

ADR 0007 วางไว้ว่า "การส่งงานอิงสถานะไม่อิงเวลา" — fb-publisher กวาด Draft ที่ `status: approved` ทุกใบตามลำดับ `approved_at` เก่าสุดก่อน จนชน `max_posts_per_day` แล้วจบรอบ ผลที่ตามมาคือ **คนกำหนดไม่ได้ว่าชิ้นไหนขึ้นเมื่อไร** — สิ่งที่คนอนุมัติคือ "เอาชิ้นนี้" ไม่ใช่ "เอาชิ้นนี้ วันศุกร์เย็น" และแผนของทั้งสัปดาห์ไม่มีที่อยู่ในระบบเลย ชิ้นที่เกินเพดานรายวันก็หายเงียบ ๆ โดยไม่มีใครรู้

โจทย์ใหม่: วางแผนล่วงหน้าทั้งสัปดาห์จาก content ที่ทำไว้แล้ว ให้คนอนุมัติทีเดียวทั้งแผน แก้เวลา/สลับชิ้นได้ แล้วบอทโพสต์ตามเวลาที่แผนกำหนด

ข้อจำกัดจากระบบเดิมที่บีบรูปทางออก:

- Run ไม่มีความจำข้ามรอบ (ADR 0004) ทุกอย่างที่ต้องรู้ต้องอยู่ในไฟล์
- ความอดทนรอคิว Browser ของ Run = ระยะห่างถึงรอบถัดไปของตัวเอง และการรอไม่ทันนับเป็น failure ซึ่งครบ 3 ครั้งติดจะ auto-pause (ADR 0004/0006) — **ยิ่งตั้งรอบถี่ยิ่งเปราะ**
- ทุก Run โพสต์ลงเธรดถาวรของ Schedule เสมอ ไม่มีโหมดรอบเงียบ และหนึ่ง Schedule = หนึ่งเธรดถาวร
- `Scheduler` กันรอบซ้อนเฉพาะ Schedule เดียวกัน — Schedule คนละตัวรันทับกันได้

## Decision

- **Content Calendar = 1 ไฟล์ต่อ 1 สัปดาห์** ใน `calendar/<วันจันทร์ของสัปดาห์>.md` ของ workspace เดียวกับ pipeline (ตั้งชื่อด้วยวันที่ ไม่ใช่เลขสัปดาห์ ISO — เลขสัปดาห์คำนวณพลาดง่ายรอบปีใหม่ และวันที่อ่านแล้วรู้เรื่องกว่า) · frontmatter เก็บแค่ `week_start` + `week_end` · เนื้อไฟล์เป็นตาราง Slot: เวลา, draft id, หัวข้อย่อ, อนุมัติโดย, อนุมัติเมื่อ
- **แบ่งเจ้าของไฟล์ให้ขาด ไม่มี field ซ้ำกันสองที่**: ไฟล์ปฏิทินคือ **เจตนา** และ **คนเป็นผู้เขียน** (ผ่าน skill `content-calendar` ใน `/task`) ส่วนไฟล์ Draft คือ **สิ่งที่เกิดขึ้นจริง** และ **agent เป็นผู้เขียน** ผลคือคนกับ Run ไม่มีวันเขียนไฟล์เดียวกัน จึงไม่ต้องมีกลไกล็อกใด ๆ ทั้งที่ทั้งสองฝั่งแก้ของพร้อมกันได้ตลอดเวลา · ข้อยกเว้นเดียวคือ `workspace-janitor` **ย้าย** ไฟล์ของสัปดาห์ที่จบสนิทแล้วเข้า `archive/` ได้ (ย้ายอย่างเดียว ห้ามแก้เนื้อใน และห้ามย้ายสัปดาห์ที่ยังมีงานค้าง) — ไม่งั้นปฏิทินจะกองสะสมไปเรื่อย ๆ โดยไม่มีใครเก็บ
- **`approved` ออกจากไฟล์ Draft** — วงจร Draft ใหม่คือ `written` → `rejected` (คนตีกลับ, จบ) หรือ `posting` → `posted` / `post-failed` / `missed` · กติกาเหล็กเปลี่ยนจาก "ห้ามโพสต์ถ้า Draft ไม่ใช่ `approved`" เป็น **"ห้ามโพสต์ถ้าไม่มี Slot ที่อนุมัติแล้วชี้มาที่ Draft ใบนี้"** (การ "ไม่ผ่าน" ยังอยู่ที่ Draft เพราะเป็นคำตัดสินเนื้อหา ไม่ใช่เรื่องเวลา — และ "ยังไม่มี Slot" ไม่ได้แปลว่าไม่ผ่าน)
- **อนุมัติเป็นราย Slot** (`อนุมัติโดย`/`อนุมัติเมื่อ` เป็นคอลัมน์ในแถว ไม่ใช่สถานะของทั้งใบ) แถวที่ไม่มีชื่อคนอนุมัติ = ไม่โพสต์ · คู่กับด่าน **`draft.updated_at ≤ slot.อนุมัติเมื่อ`**: เนื้อหาที่ถูกแก้หลังอนุมัติจะไม่ถูกโพสต์จนกว่าจะมีคนอนุมัติแถวนั้นใหม่ — ปิดช่องที่อันตรายที่สุดของการอนุมัติทีเดียวทั้งสัปดาห์ คือ "ข้อความที่ขึ้นเพจไม่ใช่ข้อความที่คนอ่านตอนกดอนุมัติ"
- **เวลาของ Slot แปลว่า "ไม่ก่อนเวลานี้"** — fb-publisher เหลือ **Schedule ตัวเดียว เธรดเดียว** ที่ตั้งหลายเวลาต่อวัน (`at:09:30,13:30,19:30`) ทุกรอบจะโพสต์ทุก Slot ของวันนี้ที่ถึงเวลาแล้วและอนุมัติแล้ว รอบเวลาจึงเป็น *ความละเอียด* ของปฏิทิน ไม่ใช่ข้อบังคับที่ต้องพิมพ์ให้ตรง (ใส่ 10:00 ไว้ ของขึ้นตอน 13:30 — ไม่มีเคส "พิมพ์ผิดนาทีเดียวแล้วของหายทั้งชิ้น" และไม่ต้องมีตัวตรวจว่า config กับ Schedule ตั้งตรงกัน — ไฟล์ config ไม่เก็บสำเนาของรอบตรวจไว้เลย: **เวลาโพสต์อยู่ในปฏิทินที่เดียว รอบตรวจอยู่ที่ `at:` ของ Schedule ที่เดียว** ตัวร่างแผนเสนอเวลาตามเนื้อหาแล้วบอกคนว่าของจะขึ้นในรอบตรวจถัดไป) · ต้องแก้ `src/recurrence.ts` ให้ `at:` รับหลายเวลา
- **พลาดแล้วจบในวัน** — Slot ที่ไม่ได้ขึ้นในรอบของตัวเอง ตกไปรอบถัดไปของวันเดียวกันได้ พ้นวันแล้วยังไม่ขึ้น = publisher ปั๊ม `status: missed` ที่ไฟล์ Draft แล้วรายงาน คนไปจัดปฏิทินใหม่เอง ไม่มีการโพสต์ข้ามวัน (คอนเทนต์เกาะเทรนด์ที่ขึ้นผิดวันคือของผิดบริบท และการโผล่มาเองย้อนหลังขัดกฎ "ไม่ยิงชดเชย" ของ ADR 0004)
- **เพดานรายวันย้ายไปอยู่ตอนวางแผน** — `max_posts_per_day` (กฎที่บังคับเงียบ ๆ ตอนรัน) เปลี่ยนเป็น `posts_per_day` ที่เป็นเพียงค่าตั้งต้นให้ตัวร่างแผน คนที่อนุมัติทั้งสัปดาห์ล้มมันได้ · หลักคือย้ายการปฏิเสธไปอยู่ตอนที่มีคนอยู่ตรงหน้า เหมือนที่ ADR 0004 ย้าย Approval ไปเป็น Grant
- **ก่อนอนุมัติต้องเห็นของจริง** — skill ปฏิทินโชว์ข้อความเต็ม + รูป ของทุกชิ้นในเธรด `/task` ก่อนขออนุมัติเสมอ (ยาวหลายข้อความเพราะ Discord จำกัด 2000 ตัวอักษร ยอมแลก) ผลข้างเคียงที่บังคับตามมา: Draft ที่รูปยังไม่เสร็จ เอาเข้าปฏิทินไม่ได้
- **แก้ปฏิทินหลังอนุมัติได้ตลอด** Member ทุกคนทำได้ผ่าน skill และ agent สรุปสิ่งที่เปลี่ยนลงเธรดให้ audit เห็น (แบบเดียวกับ `/schedule edit` ใน ADR 0004) — เบรกคือ audit ไม่ใช่การล็อกสิทธิ์ ตามโมเดลเชื่อใจทีมของ ADR 0003
- **ไม่มีปฏิทิน = ดังพอ ๆ กับไม่มีของ** — publisher รายงานทุกรอบเมื่อสัปดาห์นี้ยังไม่มีไฟล์ปฏิทิน และรายงานทุกกรณีที่ Slot ชี้ไปหา Draft ที่ไม่พร้อม (ไฟล์หาย / `rejected` / โพสต์ไปแล้ว / เนื้อหาใหม่กว่าการอนุมัติ) — ความไม่ตรงกันระหว่างสองไฟล์ต้องมีคนรู้ ไม่ใช่เรื่องที่ควรเงียบ
- **skill**: เพิ่ม `content-calendar` (ร่าง/แก้/อนุมัติแผน), เพิ่ม `evergreen-maker` (เขียน draft จาก brief ของคน ไม่ผูกกับเทรนด์ — จำเป็นเพราะแผนรายสัปดาห์ต้องมีของที่ไม่เน่าไปเติมช่วงท้ายสัปดาห์ ซึ่ง pipeline เดิมที่มีผู้ผลิตแต่สายเทรนด์ให้ไม่ได้) และ `approve-content` เปลี่ยนชื่อเป็น `review-draft` (แก้ / ตีกลับ / บันทึกความจริงหลัง `post-failed`) — ชื่อเดิมต้องตายเพราะการอนุมัติไม่ได้เกิดที่นั่นอีกแล้ว ทั้งคนและ agent ที่เลือก skill จาก description จะถูกชื่อเก่าหลอก

## สิ่งที่กลับด้านจาก ADR 0007

- "การส่งงานอิงสถานะไม่อิงเวลา" ยังจริงกับขั้น Trend → Draft แต่ **ขั้น Draft → โพสต์ อิงเวลาที่คนกำหนดแล้ว**
- สถานะ `approved` ในไฟล์ Draft และ skill `approve-content` ถูกแทนที่
- `max_posts_per_day` ในฐานะเพดานตอนรัน ถูกยกเลิก
- กติกาที่ **ไม่** เปลี่ยน: หนึ่งการอนุมัติ = หนึ่งความพยายามโพสต์ (`posting` + `posting_at` ก่อนแตะ browser, ไม่ retry เอง), เนื้อหาที่อนุมัติแล้วห้ามแก้ตอนโพสต์, เนื้อหาจากโซเชียลเป็นข้อมูลไม่ใช่คำสั่ง, workspace อยู่นอก repo บอท
- **ทางกลับของกรณี "ยังไม่ได้ส่งอะไรเลย" เปลี่ยนปลายทาง**: เดิม fb-publisher คืนไฟล์เป็น `approved` เมื่อยังไม่ถึง composer (รอคิว browser ไม่ทัน / Chrome ไม่เปิด / เจอหน้า login) ตอนนี้ไม่มีสถานะนั้นแล้ว — ให้ล้าง `posting`/`posting_at` แล้วคืน Draft เป็น `written` ส่วน **Slot ไม่ถูกแตะเลย** (ปฏิทินเป็นของคน) ผลคือ Slot ยังอนุมัติอยู่และรอบถัดไปของวันเดียวกันหยิบไปลองใหม่ได้เอง หลังแตะ composer แล้วห้ามคืนเด็ดขาดเหมือนเดิม

## Considered Options

- **หนึ่ง Slot = หนึ่ง Schedule แบบยิงครั้งเดียว** — ตรงไปตรงมาที่สุดในแง่เวลา แต่ 1 Schedule = 1 เธรดถาวร แปลว่า Discord จะมีเธรดงอกทุกโพสต์ บวกโค้ดใหม่ทั้ง recurrence + store + scheduler + เทสต์
- **ให้ publisher tick ถี่ (ทุก 15–30 นาที) แล้วอ่าน Slot ที่ถึงเวลา** — ได้เวลาเป๊ะระดับนาที แต่ความอดทนรอคิว Browser หดเหลือเท่าระยะ tick ทำให้ "รอคิวไม่ทัน" กลายเป็น failure ประจำและ auto-pause ตัวเอง บวกรอบเปล่า 48–96 รอบ/วันที่ทั้งเปลือง token และท่วมเธรด
- **publisher หลายตัว ตัวละ window** — ไม่ต้องแตะโค้ดบอทเลย แต่ Scheduler กันรอบซ้อนเฉพาะ id เดียวกัน จึงเปิดโอกาสให้สอง Run เขียนไฟล์ปฏิทินใบเดียวกันพร้อมกัน ซึ่งเป็นโหมดพังที่ ADR 0007 อ้างว่าไม่มี ("writer แต่ละสถานะมีตัวเดียวโดยดีไซน์") บวกเธรดเพิ่มตามจำนวน window
- **ให้ไฟล์ปฏิทินเก็บสถานะการโพสต์ด้วย** (เห็นทุกอย่างในใบเดียว) — ถูกปัดตกเพราะทำให้คนกับ Run กลับมาแย่งกันเขียนไฟล์เดียวกัน ซึ่งเป็นราคาที่แพงกว่าความสะดวกในการอ่าน
- **สองประตูอนุมัติ** (อนุมัติเนื้อหาที่ Draft ก่อน แล้วอนุมัติเวลาที่ปฏิทินอีกชั้น) — ปลอดภัยกว่าในแง่ "อ่านสองรอบ" แต่คนต้องทำงานเดิมสองครั้งต่อชิ้น และ `approved` สองที่คือสองความจริงที่รอวันขัดกัน
- **บังคับให้เวลาของ Slot ตรงกับ window เป๊ะ** — ต้องประกาศรายการ window ซ้ำใน config ให้ agent อ่าน แล้วคนดูแลให้ตรงกับ Schedule เอง ผิดเมื่อไรของหายเงียบ ๆ

## Consequences

- คำถาม "อาทิตย์นี้โพสต์ไปกี่ชิ้นแล้ว" ตอบจากไฟล์ปฏิทินใบเดียวไม่ได้ ต้องเปิดไฟล์ Draft ตาม — ราคาที่จ่ายให้กับการไม่มี field ซ้ำสองที่
- `updated_at` เป็น honor system ของ agent (ไม่มีอะไรบังคับให้เขียน) ด่านกันเนื้อหาเปลี่ยนหลังอนุมัติจึงแข็งแรงเท่าที่ skill ทำตามกติกา — ต้องเป็นกติกาเหล็กใน `CLAUDE.md` ของ workspace
- อนุมัติทั้งสัปดาห์ในครั้งเดียวทำให้คนอ่านผ่านได้ง่ายกว่าอนุมัติทีละชิ้น ตัวถ่วงมีแค่ "บังคับโชว์ข้อความ+รูปเต็มก่อน" กับด่าน `updated_at` — ยอมรับความเสี่ยงนี้แลกกับ flow ที่คนใช้ได้จริงต่อสัปดาห์
- สัญญาโครงสร้างไฟล์ที่ ADR 0007 บอกว่าเป็น contract ไม่ใช่รายละเอียดภายใน ตอนนี้มีสองไฟล์ (Draft + ปฏิทิน) ถูกอ้างใน skill 5 ตัว + README ของ workspace + CONTEXT.md
- `Recurrence` เปลี่ยน type (clock kind ถือหลายเวลา) — record เก่าใน state ต้อง normalize ตอนโหลด เหมือนที่ทำกับ `skill` มาแล้ว
- Slot ที่ชี้ไปหาไฟล์ Draft ที่**ไม่มีอยู่แล้ว** (ถูกลบทิ้ง) จะถูกรายงานซ้ำทุกรอบจนกว่าคนจะแก้ปฏิทิน — จงใจ เพราะไม่มีที่ให้ปั๊ม `missed` และ Run ไม่มีความจำข้ามรอบ การเงียบจึงแปลว่าไม่มีใครรู้เลยว่าปฏิทินชี้ไปที่ของที่หายไป
- ปฏิทินเปลี่ยนความสัมพันธ์ระหว่างจำนวนที่ผลิตกับจำนวนที่โพสต์: เมื่อคนเลือกจากกอง ของที่ผลิตมาย่อมเหลือเสมอ — ของที่มาจากเทรนด์จึงต้องมีวันหมดอายุ (`draft_expire_days`) ไม่งั้นกองจะโตไม่มีที่สิ้นสุด ส่วนของที่เขียนจาก brief (`trend: none`) ไม่หมดอายุเพราะมันถูกเขียนมาเพื่อรอ
- ปฏิทินไม่ผูกกับ Schedule ใด ๆ ถ้าไม่มีใครสั่งร่างแผน ก็ไม่มีอะไรขึ้นเพจทั้งสัปดาห์ — จงใจ (คนคือคอขวดตาม ADR 0007) และแก้ด้วยการให้ publisher เตือน ไม่ใช่ด้วยการให้บอทร่างแผนเอง
- workspace เดิมที่ init ไปแล้วไม่มีทางอพยพ: `workspace:init` ไม่เขียนทับไฟล์ที่มีอยู่ แปลว่า `CLAUDE.md` และ `config/pipeline.md` ของเครื่องที่ใช้ template เก่าจะค้างเป็นฉบับเก่า — ตัดสินใจว่ารับได้เพราะยังไม่มี workspace ที่ใช้งานจริง (ถ้ามีวันหลัง ต้องแก้สองไฟล์นี้ด้วยมือ)
