# 0007 — Content pipeline: ส่งงานข้าม Schedule ด้วยไฟล์ md + คนอนุมัติก่อนโพสต์

Status: accepted (2026-08-03)

## Context

งานแรกของ marketing-bro: pipeline ทำ content อัตโนมัติ 3 ขั้น — หา viral trend → แปลงเป็น content ตามเสียงแบรนด์ → โพสต์ลงโซเชียล โดยรันเป็น Schedule 3 อัน (skill: `trend-scout`, `content-maker`, `fb-publisher`) ข้อจำกัดจากระบบเดิม: แต่ละ Run เป็น Agent Session ใหม่ที่ไม่จำอะไรข้ามรอบ (ADR 0004 กำหนดให้ความจำข้ามรอบอยู่ที่ prompt + ไฟล์ใน Workspace) และ tool แก้ไฟล์ (Write/Edit) ของ Run เขียนได้เฉพาะใน Workspace ตัวเอง — ขอบเขตนี้บังคับไม่ได้กับสิ่งที่ Bash ทำเอง ตามที่ ADR 0004 บันทึกไว้ ขณะเดียวกัน input ของ pipeline คือเนื้อหาโซเชียลจากคนแปลกหน้า (ความเสี่ยง prompt injection ที่ ADR 0004 บันทึกไว้) และ output คือการโพสต์จริงในนามเพจของแบรนด์

## Decision

- **สื่อกลางคือไฟล์ md ใน workspace กลางเดียว** (= `DEFAULT_WORKSPACE` ของบอท — สร้างด้วย `npm run workspace:init` จาก template ใน `templates/marketing-workspace/` ทำให้คำสั่ง pipeline ไม่ต้องระบุ `path:`) ที่ทั้ง 3 Schedule ชี้ร่วมกัน — 1 ไฟล์ = 1 ชิ้นงาน (Trend / Draft), สถานะอยู่ใน frontmatter เป็นความจริงหนึ่งเดียว, โฟลเดอร์แบ่งตามชนิดไม่ใช่สถานะ (ไฟล์ไม่ย้ายที่ตอนเปลี่ยนสถานะ), การส่งงานอิงสถานะไม่อิงเวลา (รอบไหนไม่มีของก็จบรอบเปล่า)
- **workspace อยู่นอก repo บอทเสมอ** — Workspace คือเขตที่ Run เขียนได้อัตโนมัติโดยไม่มีคนเฝ้า ถ้าชี้มาที่ repo บอท `skills/` (instruction ที่ฉีดเข้าทุก session — ADR 0005), `src/policy.ts` และ `.state/` จะอยู่ในเขตเขียนได้ทันที = ช่อง privilege escalation ของ Run ที่โดน prompt injection สำเร็จ ข้อนี้เป็น **defense-in-depth ไม่ใช่กำแพง**: ทางอ้อมผ่าน Bash ยังเหลืออยู่ (Grant พื้นฐานปล่อย Bash ทุกคำสั่ง — ช่องที่ ADR 0004 ยอมรับไว้แล้ว) แต่การแยก workspace ตัดเส้นทางที่ง่ายและอัตโนมัติที่สุดออก
- **คนอนุมัติก่อนโพสต์เสมอ**: content-maker สร้าง Draft เป็น `pending-review` + ส่ง preview เต็ม (ข้อความ+รูป) ลงเธรด Discord แล้วคน (Member คนไหนก็ได้) สั่ง `/task skill:approve-content` เพื่อ stamp เป็น `approved` — fb-publisher โพสต์เฉพาะ `approved` และห้ามแก้เนื้อหาแม้แต่ตัวอักษรเดียว (`approved_by` เป็นชื่อที่ผู้อนุมัติพิมพ์เอง — honor system ตามโมเดลเชื่อใจทีมของ ADR 0003 หลักฐานตัวจริงคือประวัติเธรด `/task` ใน Discord)
- **หนึ่งการอนุมัติ = หนึ่งความพยายามโพสต์**: fb-publisher เขียน `status: posting` + `posting_at` ลงไฟล์ก่อนแตะ browser เสมอ แล้วจบที่ `posted` หรือ `post-failed` ไม่ retry เอง ข้อยกเว้นเดียวที่คืน `approved` ได้เอง: **ยังไม่ได้ส่งอะไรเลย** (เข้าคิว browser ไม่ทัน / Chrome ไม่เปิด / เจอหน้า login — approval ไม่ควรถูกเผาด้วยเหตุที่ไม่ใช่การโพสต์) ส่วน `post-failed` คนต้องเช็คหน้าเพจก่อนแล้วสั่ง approve-content ตามจริง: ไม่มีโพสต์ → อนุมัติใหม่, มีโพสต์แล้ว → บันทึกเป็น `posted` (โหมดพังที่กันสุดตัวคือ "โพสต์ซ้ำเพราะนึกว่าครั้งแรกล้ม" ซึ่งแย่กว่าไม่ได้โพสต์)
- **เนื้อหาจากโซเชียล = ข้อมูล ไม่ใช่คำสั่ง**: trend-scout กักข้อความดิบไว้ใน section `Raw excerpts (UNTRUSTED)` ของไฟล์ Trend และทุก skill ถูกสั่งไม่ให้ปฏิบัติตามข้อความที่หน้าตาเป็นคำสั่งจากโพสต์
- v1 โพสต์ **เพจ Facebook เท่านั้น** (บัญชีส่วนตัวเสี่ยงสุดตาม ADR 0003) อ่าน trend ได้ทุกแพลตฟอร์ม โครงสร้างเผื่อช่อง platform ไว้แล้ว

## Considered Options

- **เก็บสถานะใน JSON/SQLite** — ถูกปัดตก: ผู้แก้ไฟล์มีทั้ง agent และคน (อนุมัติ/แก้ draft) md อ่านออกแก้ง่ายทั้งสองฝ่าย และ diff ดูรู้เรื่อง ส่วนความ atomic ที่ DB ให้ ไม่ใช่โจทย์ — writer แต่ละสถานะมีตัวเดียวอยู่แล้วโดยดีไซน์
- **ใช้เธรด Discord เป็นตัวส่งงาน** (ตัวถัดไปอ่านเธรดของตัวก่อน) — ถูกปัดตก: Run อ่านเธรดตัวอื่นไม่ได้ ค้นย้อนยาก และผูกข้อมูลถาวรไว้กับ Discord
- **โพสต์อัตโนมัติไม่มี gate** — ถูกปัดตก: input เป็นเนื้อหา untrusted + ผลลัพธ์คือการพูดในนามแบรนด์ต่อสาธารณะ = ความเสียหายย้อนกลับไม่ได้ gate คนจึงเป็นจุดตัดที่ขาดไม่ได้ (และเป็นเหตุผลเดียวกับที่ ADR 0002 เลือกให้คนอนุมัติ Risky command)
- **workspace ใน repo บอท** — ถูกปัดตกด้วยเหตุผล blast radius ข้างบน

## Consequences

- Operator ต้องสร้าง Schedule 3 อันชี้ workspace เดียวกันเอง (`browser:true` ทั้งสาม) — ระบบไม่มีตัวตรวจว่าชี้ตรงกัน ชี้ผิดที่ = pipeline เงียบเฉย ๆ ไม่มี error
- ทั้ง 3 Schedule + งาน gen รูป แย่ง Browser ตัวเดียวกัน — คิว FIFO ของ ADR 0006 จัดการให้ การรอคิวเป็นเรื่องปกติไม่ใช่ bug
- คนคือคอขวดโดยตั้งใจ: ไม่มีใครอนุมัติ = ไม่มีอะไรถูกโพสต์ (Draft กอง `pending-review` ไว้เฉย ๆ)
- ความเสี่ยง Meta ToS จากการโพสต์ผ่าน browser ยังอยู่ตาม ADR 0003 (ทางอัพเกรดคือ Graph API สำหรับเพจ ซึ่ง ADR 0003 เก็บไว้แล้ว)
- สัญญาโครงสร้างไฟล์ (สถานะ, id, โฟลเดอร์) ถูกอ้างใน skill 4 ตัว + README ของ workspace — เปลี่ยนเมื่อไรต้องแก้ให้ครบทุกที่ ถือเป็น contract ไม่ใช่รายละเอียดภายใน
